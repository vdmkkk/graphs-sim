# НИР7 — данные: источники, формат, сбор

Всё ниже проверено вживую 16.10.2026.

## 1. Источники

### 1.1. Карта ONEmesh (`https://map.onemesh.ru`)

Российский форк [liamcottle/meshtastic-map](https://github.com/liamcottle/meshtastic-map) с
разбивкой по городам. Данные приходят на карту через собственный MQTT-брокер ONEmesh.

- Москва — топик `msh/RU/MSK`: 1618 узлов, из них ~980 активны за сутки.
  Регион «Москва и Подмосковье» — топик `MSK-KOR-SHL-MYT-POD-DMD-ODC-KGS-RAM-HIM-IVT-PSH`: 1816 узлов.
- Москва с 16.04.2026 работает на пресете **MEDIUM_FAST** (SF9, BW 250 кГц, CR 4/5), регион RU.
- История на карте короткая: записи БД начинаются с **08.10.2026**, координаты хранятся 30 дней.

**Список узлов** (API `/api/v1/nodes` отдаёт пустой список — карта берёт узлы из кэша):

GET /cache/nodes_msk_optimized_v2.json

Заполненность (Москва, 16.10): координаты 47 %, высота 34 %, списки соседей 6 % (460 рёбер с SNR),
загрузка канала / air_util_tx 16 %, напряжение 15 %, прошивка 100 %.

**API по узлу** (все с `?root_topic=msh/RU/MSK`):

### 1.2. MQTT-брокер ONEmesh — основной источник

Параметры опубликованы самим ONEmesh на `https://map.onemesh.ru/mqtt.html`.

| параметр | значение |
|---|---|
| адрес | `mqtt.onemesh.ru:8883`, TLS |
| пароль | `onecat` |
| топик | `msh/RU/MSK/#` (интеграциям разрешено только `msh/RU/#` или `msh/RU/XXX/#`) |
| логин | **`onemeshd`** (см. ниже) |

Особенности логинов (проверено):

- `onemesh` (по умолчанию) — downlink выключен сервером, **не приходит ничего**;
- `onemeshz` — zero-hop: сервер **обнуляет hop_limit**, число хопов посчитать нельзя;
- `onemeshd` — заголовки без изменений. Мы только подписываемся и ничего не публикуем,
  поэтому в радиосеть от нас ничего не уходит.
- Логины с суффиксом `t` — троттлинг (часть пакетов фильтруется) — не подходят.

Поток: ~2,3 пакета/с только по Москве (≈200 тыс./сутки), 56–76 разных шлюзов за 2 минуты.

Пакет — protobuf `ServiceEnvelope { packet: MeshPacket, channel_id, gateway_id }`.
Заголовок `MeshPacket` открыт; полезная нагрузка зашифрована ключом канала по умолчанию
(PSK `AQ==` → ключ `1PG7OiApB1nwvP+rz05pAQ==`, AES-128-CTR,
nonce = id пакета (u64 LE) ‖ from (u32 LE) ‖ 0 (u32)).

## 2. Формат собранных данных

```
data/raw/
  mqtt/YYYY-MM-DD/HH.jsonl          # 2-часовые чанки (UTC, HH = 00, 02, …, 22)
  onemesh/cache/<YYYYMMDD_HHMM>/    # кэш узлов, каждые 2 ч: nodes.json, topics.json, hardware_models.json
  onemesh/full/<YYYYMMDD_HHMM>/     # раз в сутки: то же + nodes/<node_id>.json (история по узлу), DONE
  status.json                       # состояние сервиса, обновляется раз в минуту
  service.log, service.lock
```

Полный снимок готов, только если в папке есть `DONE` (JSON: `finished`, `nodes`, `saved`,
`failed`). Папки без `DONE` — незаконченные; в анализ не брать.

Одна строка `mqtt/*.jsonl` = один пакет, услышанный одним MQTT-шлюзом:

| поле | смысл |
|---|---|
| `t` | время приёма сборщиком (unix, с) |
| `topic`, `channel_id`, `gateway_id` | топик MQTT, имя канала, шлюз (`!xxxxxxxx`) |
| `from`, `to`, `id`, `channel` | отправитель, получатель (4294967295 = broadcast), id пакета, хэш канала |
| `rx_snr`, `rx_rssi` | SNR (дБ) и RSSI (дБм) **на шлюзе** — характеристика последнего хопа |
| `hop_start`, `hop_limit` | пройдено хопов = `hop_start − hop_limit`; 0 → шлюз слышал отправителя напрямую |
| `relay_node` | последний байт ID последнего ретранслятора (1 байт → неоднозначность 1/256) |
| `next_hop`, `via_mqtt`, `want_ack`, `priority`, `transport_mechanism`, `rx_time` | прочие поля заголовка |
| `enc` | `plain` (шлюз отдал расшифрованным), `default_key` (расшифровали мы), `channel` (частный канал — не расшифровать), `pki` (личное сообщение) |
| `portnum` | тип нагрузки: `POSITION_APP`, `TELEMETRY_APP`, `NODEINFO_APP`, `NEIGHBORINFO_APP`, `TRACEROUTE_APP`, `MAP_REPORT_APP`, `ROUTING_APP`, … |
| `payload` | разобранная нагрузка (ключи в camelCase, как в `MessageToDict`) |
| `text_len` | для текстовых сообщений — только длина, без содержимого |

Из нагрузки выбрасываются `longName`, `shortName`, `publicKey`, `macaddr`.

Состав за первые минуты: POSITION 29 %, TELEMETRY 23 %, NODEINFO 18 %, STORE_FORWARD 9 %,
ROUTING 6 %, TRACEROUTE 2 %, MAP_REPORT 1 %; расшифровано 90 % пакетов.

Первый живой запуск на постоянной машине (16.10.2026, 21:30 UTC, 165 с): 364 пакета
(2,2 пакета/с), 75 шлюзов, 61 отправитель; `enc`: default_key 79 %, pki 15 %, plain 5 %,
channel 1 %. hop_limit не обнуляется: значения 0…7, один пакет на разных шлюзах даёт
плавный градиент.

**Что учесть в анализе** (выяснено на живых данных):
- `hop_limit = 0` — нормально: пакет израсходовал все хопы (при `hop_start = 7` — 7 хопов).
- Собственные пакеты шлюза (`gateway_id` == `from`) не прошли через эфир: `rx_snr = rx_rssi = 0`.
  Для анализа линий их исключать (≈10 % записей).
- Часть шлюзов иногда отдаёт `rx_snr = 0` и `rx_rssi = 0` — это «нет данных», а не 0 дБ.
- На брокере лежат retained-сообщения (5 шт., `rx_time = 0`), которые он повторяет при каждой
  подписке. С 16.10.2026 21:42 UTC сборщик их пропускает (счётчик `retained` в `status.json`);
  в записях до этого момента они есть (21:30:16, 21:39:09, 21:40:10) — убираются дедупликацией
  по `(gateway_id, from, id)` и правилами выше.
- Темп сильно зависит от времени суток: днём ~2,3 пакета/с, ночью (00:40 МСК) ~0,5–1 пакет/с.

**Дубликаты.** Один и тот же пакет слышат несколько шлюзов — это ценно (разные приёмники одной
передачи). Дубль при анализе — совпадение `(gateway_id, from, id)`; если два сборщика работали
одновременно, такие строки удаляются.

Объём: ~540 байт/запись → ~110 МБ/сутки MQTT + ~30 МБ/сутки полных снимков ≈ 3 ГБ за 3 недели.

## 3. Развёртывание на постоянно включённой машине

```
git clone https://github.com/vdmkkk/graphs-sim.git && cd graphs-sim/НИР7
python3 -m venv .venv && . .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m collector.service                        # проверка в консоли, Ctrl+C
```

Постоянный запуск — Linux (systemd), файл `/etc/systemd/system/nir7-collector.service`:

```
[Unit]
Description=NIR7 Meshtastic data collector
After=network-online.target
Wants=network-online.target

[Service]
User=ПОЛЬЗОВАТЕЛЬ
WorkingDirectory=/ПУТЬ/graphs-sim/НИР7
ExecStart=/ПУТЬ/graphs-sim/НИР7/.venv/bin/python -u -m collector.service
Restart=always
RestartSec=30
MemoryMax=1G
StandardOutput=append:/ПУТЬ/graphs-sim/НИР7/data/raw/service.log
StandardError=append:/ПУТЬ/graphs-sim/НИР7/data/raw/service.log

[Install]
WantedBy=multi-user.target
```

`User=` обязателен: без него сервис работает от root и файлы в `data/raw` становятся root-овыми.
`service.log` создать заранее от своего пользователя (`touch data/raw/service.log`).
Без sudo — тот же юнит в `~/.config/systemd/user/` (без `User=`, `WantedBy=default.target`),
`systemctl --user enable --now nir7-collector` и `loginctl enable-linger $USER`.

```
sudo systemctl daemon-reload && sudo systemctl enable --now nir7-collector
systemctl status nir7-collector; cat data/raw/status.json
sudo systemctl restart nir7-collector     # после правки кода
sudo systemctl stop nir7-collector        # остановить (disable — убрать из автозапуска)
```

Без systemd: `./run_service.sh` (Linux) или `run_service.bat` (Windows, переменная `PYTHON`).
На Windows — отключить сон в схеме электропитания.

Поведение сервиса при сбоях:
- **Перезапуск не сбивает расписание**: время следующего кэша и полного снимка считается от
  последних папок на диске; незаконченный полный снимок моложе суток докачивается (готовые
  узлы пропускаются), а не начинается заново.
- **Второй экземпляр не стартует** (блокировка `data/raw/service.lock`, выход с кодом 2) —
  иначе записи задвоятся.
- **Тишина MQTT** дольше 10 мин (`--stall-min`) → выход с кодом 1, супервизор перезапускает.
- Сбой кэша — повтор через 10 мин; сбой полного снимка (20 узлов подряд без ответа) — докачка
  через 1 ч. Пустой ответ кэша считается ошибкой (не пишется пустой `nodes.json`).
- `client_id` MQTT случайный: брокер разрывает старую сессию при совпадении id, и два клиента
  с одинаковым id переподключались бы каждые 2–4 с.
- SIGTERM (`systemctl stop`) корректно закрывает файл; fsync — каждые 5 с.

Проверка здоровья: в `status.json` поле `last_mqtt_message` должно быть не старше пары минут
(`started` — время последнего старта процесса, счётчики `mqtt` — с этого момента). Самая свежая
папка `onemesh/cache/` — не старше 2 ч, `onemesh/full/` с `DONE` — не старше суток;
`full_progress` показывает ход текущего снимка.

## 4. Этика и правила

- Только служебные метаданные; текст сообщений, имена, ключи не сохраняются.
- В отчётах ID узлов анонимизируются, координаты — не точнее, чем в исходных данных.
- Подписка только на `msh/RU/MSK/#`, только чтение, никакого downlink в радиосеть.
- Пользователь спросит у админов ONEmesh исследовательский доступ / архив (16.10.2026).
